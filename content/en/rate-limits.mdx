## Two Rate Limits

Requests are counted twice, against two independent limits. Both return
`429 RATE_LIMITED`.

| Limit | Counted per | Applies to |
|---|---|---|
| **100 requests / second** | **API key** | every authenticated endpoint |
| **500 requests / minute** | **client IP** | every endpoint, authenticated or not |

The per-key limit is the one an integration meets first: a loop that sends
without pacing hits 100/s long before it hits 500/min. Its error message names
the limit — `Rate limit exceeded: 100 requests/second per API key.`

The per-minute limit is **per client IP, not per tenant**. Two workspaces
calling from the same egress IP share it; one workspace calling from several
IPs gets one allowance per IP.

## Rate Limit Headers

Every response includes rate limit info:

```http
x-ratelimit-limit: 500
x-ratelimit-remaining: 245
x-ratelimit-reset: 47
```

`x-ratelimit-reset` is the number of **seconds remaining** in the current window,
not a Unix timestamp. On a 429 the response also carries a `retry-after` header,
in seconds.

<Callout type="info">
These headers describe the **500/minute per-IP** limit only. The per-key
limit of 100/second is not reflected in them: you can be at
`x-ratelimit-remaining: 400` and still get a 429 for sending 100 requests in
the same second.
</Callout>

## Check Rate Limit Status

Before hitting the limit, check the headers:

```bash
curl -i https://api.tratto.email/v1/emails \
  -H "Authorization: Bearer tratto_live_..."
```

Returns headers with remaining requests and reset time.

## Rate Limit Exceeded (429)

When you exceed the limit:

```json
{
  "error": {
    "code": "RATE_LIMITED",
    "message": "Too many requests. Slow down.",
    "docs": "https://tratto.email/docs/api/errors#rate_limited"
  }
}
```

The response carries no `retryAfter` field. Use the `x-ratelimit-reset` header
and your own backoff.

## Retry Strategy

Use **exponential backoff with jitter**:

```javascript
async function sendWithRetry(request, maxRetries = 3) {
  for (let attempt = 0; attempt < maxRetries; attempt++) {
    try {
      return await fetch(request);
    } catch (error) {
      if (error.status === 429) {
        const delay = Math.pow(2, attempt) * 1000 + Math.random() * 1000;
        await new Promise(r => setTimeout(r, delay));
      } else {
        throw error;
      }
    }
  }
}
```

## Plan Limits

There are three plans, and two caps on each:

| Plan | Emails per month | Verified domains |
|---|---|---|
| Free | 3,000 | 1 |
| Starter | 75,000 | 5 |
| Growth | 500,000 | unlimited |

There is **no per-day cap** on a plan. The only daily limit in the product is
the test-mode one — 100 test sends per day, see
[Test Mode](/en/docs/test-mode).

Exceed the monthly quota and requests fail with `QUOTA_EXCEEDED`, which also
returns 429. Unlike `RATE_LIMITED` it will not clear by retrying: see
[Error Codes](/en/docs/error-codes).

### Read your own limits from the API

Do not hard-code the numbers above. `GET /v1/workspace` returns the limits
that are actually enforced on your workspace, and `null` means no limit:

```bash
curl https://api.tratto.email/v1/workspace \
  -H "Authorization: Bearer tratto_live_..."
```

```json
{
  "data": {
    "plan": "free",
    "limits": { "emailsPerMonth": 3000, "domains": 1 }
  }
}
```

This is the same table the enforcement reads, so it cannot disagree with what
you are actually allowed to send.

### The month is a UTC calendar month

The quota is **not** a rolling 30-day window. The counter is keyed on the UTC
calendar month (`2026-09`), and it rolls over on your **first send of the new
month** — there is no scheduled reset job. A workspace that sends nothing in
October still starts November at zero, on its first November send.

<Callout type="warn">
**There is no "Pro" plan, and no unlimited tier.** `free`, `starter` and
`growth` are the only three. Some early workspaces still carry a legacy plan
value of `pro` in storage; it is not recognised, so it resolves to **free** —
3,000 emails per month and 1 verified domain — both in what is enforced and in
what `GET /v1/workspace` reports back (that endpoint answers `"plan": "free"`
for such a workspace, not `"pro"`).
</Callout>

## Burst Behavior

Short bursts (seconds) can exceed `x-ratelimit-remaining` due to asynchronous processing. The 500 req/min limit is a hard cap; short peaks are allowed if average stays under the limit.
