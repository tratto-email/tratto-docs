Una **campagna** è una trasmissione email una tantum a un'audience. Crea una campagna, opzionalmente testala, poi inviala a centinaia o migliaia di destinatari.

## Crea una Campagna (Draft)

Crea una campagna in status draft. **`name`, `subjectA` ed esattamente uno fra
`templateId` e `html` sono obbligatori**: se ometti `subjectA` la richiesta
fallisce con 422.

**cURL**
```bash
curl -X POST https://api.tratto.email/v1/campaigns \
  -H "Authorization: Bearer tratto_live_..." \
  -H "Content-Type: application/json" \
  -d '{
    "name":"Saldi Estivi Q3",
    "subjectA":"I saldi estivi iniziano oggi",
    "templateId":"tmpl_abc123",
    "audienceId":"aud_abc123"
  }'
```

**Risposta:** l'id, e nient'altro.
```json
{
  "data": {
    "id": "camp_xyz789"
  }
}
```

Usa `GET /v1/campaigns/{id}` per leggerne status, contenuto e statistiche.

**Campi del body:**

| Campo | Obbligatorio | Note |
|---|---|---|
| `name` | sì | max 200 caratteri |
| `subjectA` | sì | l'oggetto, max 998 caratteri |
| `subjectB` | no | secondo oggetto per un test A/B |
| `templateId` | uno dei due | copia il contenuto del template nella campagna. **Esattamente uno** fra `templateId` e `html`: entrambi, o nessuno, è un 422. Il template deve essere `published`, altrimenti la richiesta è un 422 anche in quel caso |
| `html` | uno dei due | HTML inline, senza bisogno di un template |
| `audienceId` | no | **omesso = tutti i contatti del workspace** |
| `fromName` | no | in mancanza, il mittente di default del workspace |
| `fromEmail` | no | in mancanza, il mittente di default del workspace |

Se né il body né il workspace forniscono un mittente, la richiesta fallisce con
422 e un messaggio che ti dice di impostare un mittente di default.

Dalla creazione in poi la campagna possiede una **copia** del contenuto del
template: modificare il template dopo non cambia una campagna già creata da
esso, e modificare la campagna non tocca il template.

<Callout type="warn">
**Il template deve essere pubblicato.** Creare una campagna da un template
`draft`, o sostituirlo con `PATCH /v1/campaigns/:id`, fallisce con **422
`TEMPLATE_NOT_PUBLISHED`** e il messaggio
`Template 'tmpl_abc123' is not published and cannot be used to send.` Un
template inesistente è invece un **404**. Pubblicalo prima: vedi
[Template](/it/docs/templates#pubblica-prima-di-inviare).

Poiché il contenuto viene copiato alla creazione, il controllo non è
retroattivo: le campagne create prima che questo gate esistesse mantengono la
loro copia e continuano a partire.
</Callout>

## Variabili di una Campagna [#campaign-variables]

Una campagna valorizza esattamente quattro variabili, risolte per destinatario
al momento dell'invio:

| Variabile | Valore |
|---|---|
| `email` | l'indirizzo email del contatto |
| `firstName` | il nome del contatto |
| `lastName` | il cognome del contatto |
| `unsubscribe_url` | il link di disiscrizione di quel contatto |

Scrivile con le graffe **doppie**, nell'oggetto e nel corpo:

```html
<p>Ciao {{firstName}}, i saldi estivi iniziano oggi.</p>
<p><a href="{{unsubscribe_url}}">Disiscriviti</a></p>
```

Tre cose decidono se funzionano.

**Maiuscole e minuscole contano.** `{{firstName}}` viene valorizzata,
`{{firstname}}` no. La grafia della tabella qui sopra è l'unica che funziona.

**Una graffa singola non è una variabile.** `{firstName}` resta intatta e il
destinatario la legge come testo. Solo `{{firstName}}` viene sostituita.

**Un nome fuori da quei quattro diventa una stringa vuota.**
`{{companyName}}` in una campagna non fa fallire l'invio, e non lascia nemmeno
il segnaposto a schermo. Sparisce, e la frase intorno arriva con un buco:
`Ciao {{companyName}} cliente` viene consegnato come `Ciao  cliente`. Niente,
nella casella del destinatario, dice che lì c'era una variabile: è per questo
che il punto in cui accorgersene è la bozza.

### Perché il controllo esiste sulle campagne e non sui template

Una campagna viene inviata a dei contatti, quindi Tratto conosce i quattro nomi
qui sopra e può segnalare tutto ciò che ne sta fuori mentre la campagna è
ancora in bozza. Un template inviato con
[`POST /v1/emails`](/it/docs/send-email) prende le variabili da chi chiama
l'API, quindi non esiste un insieme chiuso contro cui verificarle e ogni
controllo sarebbe un'ipotesi. Su un template l'unica difesa è passare a ogni
invio tutti i segnaposto che il template usa. Vedi
[Template](/it/docs/templates#2-passa-sempre-tutte-le-variabili).

## Invio di Test

Invia un'email di test prima del lancio per assicurarti che tutto appaia corretto.

**cURL**
```bash
curl -X POST https://api.tratto.email/v1/campaigns/camp_xyz789/test-send \
  -H "Authorization: Bearer tratto_live_..." \
  -H "Content-Type: application/json" \
  -d '{"to":"your-email@example.com"}'
```

Un'email di test viene inviata al tuo indirizzo immediatamente.

## Invia Immediatamente

Invia la campagna a tutti i contatti nell'audience proprio adesso.

**cURL**
```bash
curl -X POST https://api.tratto.email/v1/campaigns/camp_xyz789/send \
  -H "Authorization: Bearer tratto_live_..."
```

**Risposta:**
```json
{
  "data": {
    "status": "sending"
  }
}
```

Lo status della campagna diventa `sending`, poi `completed` a invio concluso.

L'invio è rifiutato con 409 se la campagna non è `draft` o `paused`, e prima di
partire viene confrontato con la
[quota mensile](/it/docs/rate-limits) residua.

**L'invio è progressivo, non istantaneo.** Le email escono con un tetto al
secondo, quindi una campagna con molti destinatari resta `sending` per un po'
prima di completarsi. È l'invio che lavora, non un guasto. Il tetto è un
parametro operativo e può cambiare: non costruire un timeout su un numero
misurato una volta sola.

In più, una campagna abbastanza grande parte con un'[ondata di
prova](#ondata-di-prova) e si ferma a metà di proposito.

## Programma per Dopo

Programma la campagna con **`scheduledAt`** (ISO 8601). Il campo non si chiama
`sendAt`.

**cURL**
```bash
curl -X POST https://api.tratto.email/v1/campaigns/camp_xyz789/send \
  -H "Authorization: Bearer tratto_live_..." \
  -H "Content-Type: application/json" \
  -d '{"scheduledAt":"2026-10-01T09:00:00Z"}'
```

Lo status della campagna diventa `scheduled` e l'invio parte automaticamente a
quell'orario. Uno `scheduledAt` nel passato equivale a «invia adesso».

Per annullare la programmazione e riportare la campagna a `draft`:

```bash
curl -X POST https://api.tratto.email/v1/campaigns/camp_xyz789/unschedule \
  -H "Authorization: Bearer tratto_live_..."
```

**Qui rispondono `409` due situazioni diverse**, e il messaggio le distingue:

- **l'invio è già partito** (`status` è `sending`): il dispatcher ha preso la
  campagna prima che tu la annullassi
- **la campagna sta aspettando la sua [ondata di prova](#ondata-di-prova)**:
  risulta `scheduled` con `scheduledReason: "bounce_check"`, ma una parte della
  lista ha già ricevuto l'email, quindi non c'è più niente da riportare a
  `draft`

In entrambi i casi metti in pausa: i destinatari già raggiunti non si possono
disinviare.

## L'Ondata di Prova [#ondata-di-prova]

Una campagna abbastanza grande non parte verso tutta la lista in una volta. Il
primo invio raggiunge un'**ondata di prova**: il 5% dei destinatari rimanenti,
mai meno di 50 e mai più di 500. Tratto aspetta poi **15 minuti**, conta quanti
di quegli indirizzi hanno rimbalzato in modo permanente, e solo allora fa
partire il resto.

**Perché esiste.** Tratto invia su un pool condiviso
([IP Warming](/it/docs/ip-warming)) e il tasso di rimbalzi permanenti è ciò che
decide se l'invio viene bloccato su quel pool, per tutti i workspace che lo
usano. Una lista mai pulita non costa solo a chi la possiede. L'ondata limita
quel costo a poche decine di email invece che all'intera lista.

**Cosa vedi mentre è in corso.** Dopo l'ondata la campagna torna
**`scheduled`** per quei 15 minuti, con uno `scheduledAt` fra un quarto d'ora.
Una campagna che non hai mai programmato può quindi risultare `scheduled` poco
dopo che l'hai inviata. Riparte da sola, e `stats.sent` conta già l'ondata.
Per tutta l'attesa **`scheduledReason`** vale `"bounce_check"`, ed è quello che
distingue questo caso da una data impostata da te: vedi
[Quale dei due `scheduled`](#scheduled-reason).

**Quando l'ondata non c'è:**

- l'ondata coprirebbe comunque tutta la lista rimanente. Non dimostrerebbe
  niente, quindi la campagna parte e si completa come prima. Le campagne
  piccole non cambiano comportamento
- la campagna ha già raggiunto qualcuno. L'ondata si fa **una volta per
  campagna**: una ripresa dopo una pausa, un orario mancato o una quota
  esaurita riparte da dove si era fermata, senza una seconda attesa

Se il tasso di rimbalzi dell'ondata supera la soglia la campagna si mette in
pausa da sola: vedi [Perché una campagna è in pausa](#motivo-della-pausa).

## Ciclo di Vita dello Status della Campagna

Gli status sono cinque: `draft`, `scheduled`, `sending`, `paused` e
`completed`. **`sent` non esiste.**

```
draft
  ├─→ (test-send)
  ├─→ send                 → sending → completed
  └─→ send + scheduledAt   → scheduled → sending → completed
                                └─→ unschedule → draft

sending ─→ ondata di prova ─→ scheduled (15 min) ─→ sending → completed
                                                └─→ paused (bounce_rate)

sending / scheduled  ─→ pause → paused ─→ send (ripresa) → sending
```

`scheduled` significa quindi due cose: un invio che hai programmato tu, oppure
una campagna che sta aspettando la sua [ondata di prova](#ondata-di-prova). Per
l'ondata non è stato aggiunto nessuno status, quindi un client che ragiona solo
su `status` non riesce a distinguere i due casi. Il campo che li distingue è
**`scheduledReason`**.

### Quale dei due `scheduled` [#scheduled-reason]

`scheduledReason` è di sola lettura, `string | null`, e torna in
`GET /v1/campaigns/{id}` e in `GET /v1/campaigns`. Oggi ha un solo valore:

| `scheduledReason` | Cosa significa | Cosa puoi fare |
|---|---|---|
| `null` | La programmazione l'hai chiesta tu, con `scheduledAt` | `unschedule` la riporta a `draft`; anche `pause` funziona |
| `"bounce_check"` | La campagna **non è programmata, sta spedendo.** È già uscita verso la sua [ondata di prova](#ondata-di-prova) e sta aspettando i 15 minuti del controllo rimbalzi | Niente: l'attesa finisce da sola. `unschedule` risponde **409**, perché una parte della lista ha già l'email e quelle non si richiamano indietro. `pause` ferma il resto |

Il campo è **additivo e nullable**: si aggiunge a campi che c'erano già, quindi
nessun client esistente si rompe ignorandolo. Quello che si rompe è dare per
scontato che ogni campagna `scheduled` si possa ancora deprogrammare.

## Pausa una Campagna

Interrompi una campagna programmata o in corso. Si può mettere in pausa solo
una campagna `sending` o `scheduled`: qualsiasi altro status è un 409.

**cURL**
```bash
curl -X POST https://api.tratto.email/v1/campaigns/camp_xyz789/pause \
  -H "Authorization: Bearer tratto_live_..."
```

**La ripresa è una nuova `POST /:id/send`** sulla campagna in pausa: non
esiste un endpoint di ripresa separato. Riparte dai soli destinatari mai
raggiunti, quindi nessuno riceve l'email due volte.

Una campagna in pausa può essere ripresa; solo una in `draft` può essere
eliminata.

### Perché una campagna è in pausa [#motivo-della-pausa]

Una campagna può anche essere messa in pausa *per te*, e `paused` da solo non
dice da chi. **`pausedReason` è il campo che distingue i casi** (l'equivalente
di [`scheduledReason`](#scheduled-reason) per una campagna `scheduled`), e ha
tre valori più `null`:

| `pausedReason` | Cosa è successo | Cosa fare |
|---|---|---|
| `null` | L'hai messa in pausa tu, con `POST /:id/pause` | Riprendila quando vuoi |
| `"quota_exceeded"` | L'invio non stava nella [quota mensile](/it/docs/rate-limits) residua, prima di partire o a metà strada | Aspetta l'azzeramento o passa a un piano superiore, poi riprendi. Raggiunge solo i destinatari mancati |
| `"schedule_missed"` | Una campagna programmata **da te** è stata presa più di un'ora dopo il suo `scheduledAt` e non è stata inviata così in ritardo | Riprendila a mano se l'invio serve ancora, oppure riprogrammala |
| `"bounce_rate"` | Troppi rimbalzi permanenti fra le email già inviate | **Pulisci la lista prima di riprendere.** Vedi qui sotto |

**`schedule_missed` vale solo per una data impostata da te.** Anche una
campagna parcheggiata per la sua [ondata di prova](#ondata-di-prova) risulta
`scheduled`, ma non viene messa in pausa così per quanto l'attesa sfori l'ora:
il resto della lista non è un invio che nessuno si aspetta più, è la fine di
quello che hai chiesto, quindi parte. Li distingue
[`scheduledReason`](#scheduled-reason): `"bounce_check"` non viene mai messa in
pausa per un orario mancato, `null` sì.

La `POST /:id/send` successiva azzera `pausedReason`: leggilo prima di
riprendere.

### Fermata sul tasso di rimbalzi [#tasso-di-rimbalzi]

Tratto conta i rimbalzi **permanenti** delle email che una campagna ha
effettivamente fatto uscire: quelli temporanei non contano. Oltre il **5%**,
con un minimo di 3 rimbalzi, la campagna si mette in pausa da sola con
`pausedReason: "bounce_rate"` e un'email arriva al proprietario del workspace.
(I due numeri sono la stessa decisione vista due volte: 3 è il 5% di 50, cioè
dell'[ondata di prova](#ondata-di-prova) più piccola.)

Il 5% è la stessa linea su cui viene giudicato il pool di invio condiviso: per
questo ci fermiamo lì e non più tardi.

**Niente riparte da solo.** Non c'è nessun tentativo automatico e nessun timer:
la campagna resta `paused` finché non la reinvii tu. È una scelta: una lista
che ha rimbalzato a quel ritmo rimbalzerà di nuovo, a meno che la lista non
cambi.

Prima di riprendere, togli gli indirizzi che hanno rimbalzato (Tratto li
sopprime per gli invii futuri, ma restano nella tua lista finché non li
elimini) e controlla da dove arriva la lista. Una campagna fermata così, quando
la riprendi, normalmente riparte con una nuova ondata di prova da 50
destinatari e la stessa attesa di 15 minuti: una lista non pulita viene quindi
ripresa dopo 50 email invece che dopo tutto il resto.

## Ottieni Statistiche Campagna

Visualizza le statistiche di consegna dopo l'invio.

**cURL**
```bash
curl https://api.tratto.email/v1/campaigns/camp_xyz789/stats \
  -H "Authorization: Bearer tratto_live_..."
```

**Risposta:** conteggi e tassi sono due oggetti distinti.
```json
{
  "data": {
    "campaignId": "camp_xyz789",
    "status": "completed",
    "stats": {
      "total": 5000,
      "sent": 5000,
      "delivered": 4950,
      "opened": 2475,
      "clicked": 742,
      "bounced": 40,
      "skipped": 12,
      "untracked": 130
    },
    "rates": {
      "deliveryRate": 99,
      "openRate": 50.82,
      "clickRate": 15.24,
      "bounceRate": 0.8,
      "untracked": 130
    }
  }
}
```

<Callout type="warn">
**I tassi sono percentuali**, arrotondate a due decimali: `99` significa 99%,
non `0.99`. Un alert scritto come `deliveryRate < 0.95` non scatterà mai: il
confronto giusto è `< 95`. Stessa scala di [Analytics](/it/docs/analytics).
</Callout>

Note sui campi:

- `total` è il numero di destinatari; `sent` conta quelli effettivamente
  inviati
- `skipped` — invii annullati perché il contatto si è disiscritto dopo il
  dispatch. Non sono mai avvenuti, quindi non alimentano nessun tasso
- `untracked` — destinatari che hanno rifiutato il tracciamento di aperture e
  click. Sono **esclusi dal denominatore di openRate e clickRate**, mai
  stimati. La chiave `untracked` dentro `rates` è quello stesso conteggio, non
  un tasso
- `stats.variants` e `rates.variants` compaiono solo su una campagna che ha
  fatto un test A/B sull'oggetto
- **Non esiste** un campo `complained`, né `totalSent`

## Elenca le Campagne

Ottieni tutte le campagne.

**cURL**
```bash
curl "https://api.tratto.email/v1/campaigns?status=completed&limit=50" \
  -H "Authorization: Bearer tratto_live_..."
```

**Parametri di query:**
- `status`: Filtra per status — `draft`, `scheduled`, `sending`, `paused`,
  `completed`. `sent` non è un valore valido e restituisce 422
- `q`: Ricerca per **prefisso** del nome, case-insensitive ma sensibile agli
  accenti (`sal` trova `Saldi estate`, `estate` no). Finché è attiva,
  l'ordinamento è per nome invece che dal più recente
- `limit`: Risultati per pagina (default 50, max 100)
- `after`: Cursor per paginazione

## Best Practice per le Campagne

### 1. Testa Sempre Prima

Invia un'email di test a te stesso prima del lancio a qualsiasi audience.

### 2. Usa Nomi Descrittivi

✅ `Saldi Estivi Q3 - Segmento Newsletter`  
❌ `Campagna 1`, `Test`

### 3. Rivedi la Dimensione dell'Audience

Conta i destinatari prima dell'invio:
`GET /v1/contacts?status=subscribed&audienceId=…` restituisce lo stesso
`pagination.total` che conta il gate d'invio. Un'audience senza contatti
iscritti significa che nessuno la riceve.

### 4. Programma Durante i Tempi Ottimali

Considera il fuso orario della tua audience quando programmi. Inizio mattina o pausa pranzo di solito vedono tassi di apertura più alti.

### 5. Monitora le Statistiche di Consegna

Dopo l'invio, esamina i tassi di rimbalzo, reclamo e apertura per comprendere l'engagement.

### 6. Crea Nuove Campagne, Non Reinviare

Una campagna raggiunge ogni destinatario una volta sola. Reinviare una campagna
`completed` è un 409; riprendere una `paused` copre solo i destinatari mai
raggiunti. Per scrivere di nuovo alla stessa audience, crea una nuova campagna.
